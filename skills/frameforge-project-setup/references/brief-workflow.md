# 立项与变更工作单

## 从输入到交付

1. **了解作者想写什么**。只有一句构想时，先问本轮最影响剧情的一两个开放问题。比如「你脑子里最先出现的是哪个人或哪一幕？可以从一个画面讲起。」用户先描述角色时，可接着问「这个人眼下最想得到什么？有什么会迫使他现在行动？」把已明确的要求和待定项记清，再按需要询问发布场景、已有素材和体量。旧作同时读取工程、章起点和素材类型。
2. **从已有构想确定最小范围**。用户要求写简报时，用用户描述的主角、处境和行动整理可玩范围，记录仍缺的创作决定。用户要求提案或授权你补全时，可按当前范围设计玩家行动与可见后果。再从场地、角色、对白和实际演出量估算体量。
3. **落规格**。分别写最终播放宽高、视图里的构图留白和参考图用途。原始素材有固定画幅时，抽取代表性素材检查人物、关键物件与同框关系。只有元数据时，只能验证尺寸和时长。预设和画风详细说明是两项：预设定义大类，描述给下游灯光、质感、线条和色彩约束。
4. **交付两个视图**。玩家简介包含身份、处境、行动和悬念。制作简报包含交付范围、镜头与资产约束、待定项。作者、结局剧透、成本和模型能力按各自用途填写。
5. **写入和回读**。用 `update_project` 发送本次改动字段。修改开场时先确定第一章和目标节点，再检查开场路径。工具成功后，实际回读 `settings` 或章节，按原请求逐项对照。

## 工作单

| 字段 | 填写内容 | 证据 |
|---|---|---|
| 创作意图 | 一句话讲清玩家做什么、失去什么 | 用户原话或已接受梗概 |
| 最小范围 | 章节、场地、具名角色、路线和体量上限 | 用户要求或本轮估算 |
| 硬规格 | 宽、高、预设、场景与声音限制 | 工程读回、源素材规格或已确认的发布需求 |
| 剧情约束 | 本轮必须保留的事实、禁改项、可提案项 | 对应原文或工程节点 |
| 待定 | 决策人、所缺信息、影响阶段 | 影响到哪一步才成为阻塞 |
| 写入记录 | 字段、原值、新值、实际回读 | `read_project` 或章节结果 |

## 已有作品换画幅

例如，用户把 1920×1080 改为 1080×1920，已有横屏素材的关键行动发生在两人之间。先列可重构的静帧、可裁切的单主体片段及需补拍的双人片段；根据现有帧证据选具体条目。工程设置和制作影响分别回报。两人是否可在竖屏同框属于素材判断。工程设置更新只证明播放画幅已变，回报时列出仍需检查或重排的素材。
