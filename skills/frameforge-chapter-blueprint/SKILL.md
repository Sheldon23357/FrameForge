# 章节蓝图

输入是指定章的非线性剧本和工程现状。用 `read_story_design` 读章节、按需查全局规则。用 `read_story.topology` 查实际入口、出边、章起点和复用节点，用 `list_game_data` 查现有参数和道具。复用真实 ID，优先读相接章节的实际入口和结尾。

1. 按场次和来路列节点计划。共用行动可以合成一个节点，选项后的独立演出、结算或知情区别需要有明确落点。建节点时按所属章、对应情节和实际前后节点写 `notes`。一个剧本场次可以拆成多个节点，各节点只写自身在该路线发生的事。
   先给同一条路线的铺垫、验证和后果找可见落点，再定节点数量。互斥分支的节点不能替主路补篇幅。重要推论的证据与判断之间留足动作或对白；汇流若使用所有来路都必须知道的事实，逐条确认已在各自来路交代，或在汇流前后补一处共同可见的验证。
2. 每个节点在「节点内容」`notes` 明确写四项，按顺序分段。
   - **从哪来**。记录前置节点或进入它的选择、时间地点和进场处境。章首注明开场，跨章注明实际入口。
   - **已知与持有**。记录进场已知事实、持有道具和状态。汇流时列共同事实及不同来路的差异。
   - **这一段新增什么**。按顺序写行动、对白意图、线索、必要声响、道具和参数变化。标出选项出现前需要玩家知道的信息。自动分支写判定意图，结局节点写收束结果。
   - **往哪去**。写自动出口或每项选择与条件的目标，以及交接的离场状态。结局注明结束。
   改剧情或连线时在任务范围内同步改受影响的节点内容。新视频节点无可绑定画面时填简短的 `storyboardPages` 占位供试玩。占位文字也按玩家阅读来写，多用自然短句，按行动、发现和反应的顺序把事情说清楚。把实际节点和四项交接交给 `frameforge-node-screenplay` 编写正式动作、对白、独白和声音，再交给分镜和玩家文字编排。
3. 先复用或创建节点，再按返回的 ID 接边。用 `edit_chapter` 指定章起点，`edit_scene.connect` 接自动播放，`edit_choice` 接玩家选择或自动条件出口，`edit_game_data` 定义参数和道具，`edit_event` 实现增减、发放、消耗和任务状态。效果在哪段演完才生效，就放在该段的 `complete`。需要自动条件分支时按优先级设置出口与兜底。结局演出用视频节点，播完转入 `ending` 总结。
4. 用 `check_story.validate` 核对引用和结构，`explore` 查可达性，`simulate` 用实际选择核对每条受影响路线的章入口、汇流、数值和道具。交付真实节点 ID、入出边、规则落点、已验证路线及制作需注意的接缝。
   完整章或全局搭建时，用 `check_story.simulate` 的 `detail=pacing` 对照代表性路线的净时长和预期篇幅。可从 `explore` 的已发现结局取 `choiceIds`；路线尚未搭完整时，核对已可走的前缀并标明落点。试玩占位时长只作初估。只按实际播放顺序读玩家文字、选项和结局，点出仍需演出的因果与反应，交给剧本和制作阶段。

## 玩家可见选项

先确定玩家这一刻能选的行动或态度，再直接写成自然、简短的按钮文字。动作选项各写一个主要行动，如「跟上他」「留在原地」。表态选项各表达一种态度，如「我信你」「我想再等等」。上下文里不明确的对象要写清楚。

条件、理由、风险和共同前提放在选择前的画面、对白、玩家正文或整组选项的问题中。按钮保留玩家做决定时必须区分的信息。每项最多 12 个字符，字数上限用于写入前验收。放不下时，调整前文和按钮各自交代的信息。不要先写长句再硬删字，也不要用缩写、生造词或把多个动作、表态与承诺挤在一条里。写入前按玩家当下知道的信息把整组选项读一遍，确认一眼就能看懂每一项、分得清它们的区别。

需要节点预算、批量落图、跨章改线或故障定位时，读[章节落图工作单](references/implementation-workflow.md)和[节点预算与修订](references/graph-and-revision.md)。需设计或调整规则体系时使用 `frameforge-game-balance`。
